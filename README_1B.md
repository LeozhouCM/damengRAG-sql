# 1B 检索与基线评测说明

> 本文件是什么：1B（向量索引 + 检索 + 20 题基线评测）的说明和实测记录。写清这一版做了什么、怎么跑、指标是什么、结果是多少、哪里失败、哪些边界没有越过。
>
> 当前状态：**2026-11-26 已在本机跑通第一条基线**；代码、20 题评测集和指标已提交，`data/index/` 按约定不进 Git，结果仍等待人工验证。质量通过线**还没有定**，这一版只提供数据，不预设“合格/不合格”。

## 1. 一句话结论

在 1A v2 的 **1,502 个子块、240 个父块、27 个来源**上，使用 `BAAI/bge-base-zh-v1.5` + Chroma + BM25/RRF 跑通“角色选子块、父块补上下文、证据单独取”的检索流程，并用 20 道自建题做基线：

- **CaseHit@1 = 95.0%**（20 题中 19 题选中了 gold 案例/手册）。
- **RoleRecall@3（每个角色平均）= 77.1%**（35 个角色实例命中 27 个）。
- **RoleGoldCoverage = 85.0%**（最终选块时，有多少必需角色拿到了 gold 父块）。
- **EvidenceCoverage = 85.7%**（14 道带证据类型题的平均；其中 q05、q09 的 gold 案例本身没有该类型，按“资料不足”解释；可评估的 12 道题是 **12/12 = 100%**）。
- **Global Recall@5 = 70.0%**（纯子块全局 top5 基线，不做角色/父块）。

这不是生产系统：只生成报告草稿，不连接生产库、不执行 SQL、不自动建索引、不替代人工判断。

## 2. 角色、父块、证据的边界（先看这一节）

这一版的分工是之前讨论后的共识，代码也按这个边界写：

- **子块是检索单位。** 建索引、算相似度、算 BM25、做 RRF，全部只针对子块。
- **角色用于“选哪些子块”。** 先按问句推断需要哪些角色（问题/原因/办法/验证，必要时加概念/步骤），再在每个角色内取候选子块。
- **父块只负责“选中之后补上下文”。** 父块不建索引、不参与排序、不做第二次检索，也不在角色选择之前做父块聚合。父块的值是：命中一个子块后，把同一标题节里前后相邻的子块按 `chunk_index` 拼回来，给报告提供可读的完整段落。
- **证据不是角色。** 执行计划/统计输出用 `content_type` 表示，单独按证据名额取；它不占“问题/原因/办法/验证”的角色名额，也不会把“原因”节误标成“执行计划”角色。
- **缺少角色不硬凑。** 角色候选里没有就记录缺失；只允许在已选案例内部补一次，补不到就保留 `missing_roles`，交给报告层降级为“资料不足/需人工确认”。

报告提纲的顺序仍是：**问题 → 证据 → 原因 → 办法 → 验证**。角色负责问题、原因、办法、验证四项的选块，证据负责“证据”一栏。

本次实测：

- 构建耗时：**173.46 秒**（CPU；主要花在 1,502 条文本的 bge 编码）。
- 索引目录大小：**11.34 MB**。
- Chroma 向量数：**1,502 / 1,502**。
- BM25 文档数：**1,502 / 1,502**。
- 模型维度：**768**；最大序列长度：**512**。
- 构建完成后脚本会关闭 client，用新 client 重开一次，确认 `count()` 和 `query()` 都正常，再退出。

### 4.2 必须从项目根目录运行（Chroma 1.5.9 的 Windows 限制）

本机实测（Chroma 1.5.9 + Windows）：把 `E:\毕业设计\...` 这种**含中文的绝对路径**传给 `chromadb.PersistentClient`，建库时 HNSW 文件写不出来，换一个进程重开就报：

```text
Error loading hnsw index
```

同一个目录改成**相对路径**（从项目根目录看是 `data/index/chroma`，全 ASCII）后，建库、关闭、重开、查询都正常。代码里的 `chroma_relative_path()` 就是把这个限制固定下来：

- 脚本必须从项目根目录运行；
- Chroma 目录的相对路径不能含非 ASCII 字符；
- 不满足时直接报错，避免又建出一个“进程内能查、重开就坏”的索引。

这不是 Chroma 官方文档里的结论，是本机复现后采用的工程规避；本项目只对“从项目根目录使用相对 ASCII 路径”这一条负责，不把底层原因归到某个未核实的 issue。

## 5. 检索流程（对应代码）

入口是 `src/knowledge/retrieval.py:search()`（第 760 行）。角色模式一次查询的步骤如下：

1. **推断角色**：`infer_required_roles()`（第 145 行）只做问句里的显式词匹配，不做语义猜测；推断不到角色时返回空列表，走全局检索。报告四类角色在前，概念/步骤等补充角色在后，最多 4 个。
2. **子块召回**：`child_recall()`（第 252 行）同时做两路：
   - dense：Chroma 余弦相似度 top 50；
   - BM25：jieba 精确模式分词 + `config/tags.yaml` 词表，top 50；
   - 用 `rrf_fuse(k=60)`（第 178 行）在**子块级**融合成一份候选列表。
3. **按角色切候选**：`role_candidates()`（第 316 行）只看子块自己的 `section_role`，每个角色按融合顺序取前 10 个**父块**，每个父块只留一个代表子块。
4. **选案例**：`select_root()`（第 369 行）先比“覆盖了几个必需角色”，再比“各角色最佳候选的 RRF 分数和”，最后用 `root_id` 排序保证同题结果稳定。
5. **按角色名额取块**：`select_role_chunks()`（第 383 行）只在选中的 root 内取；每个角色每个父块最多一个子块。名额来自 `config/settings.yaml`：

   | 角色 | 名额 |
   | --- | ---: |
   | 问题 | 2 |
   | 原因 | 3 |
   | 办法 | 3 |
   | 验证 | 2 |
   | 概念/步骤等补充角色 | 默认 2 |

6. **缺角色补一次**：`backfill_missing_roles()`（第 410 行）只对缺失角色，在已选 root 内做一次局部召回；补不到就保留缺失，不无限重试。
7. **父块展开**：`expand_parent()`（第 457 行）对每个选中的子块，取同一父块内前后各 2 块；**命中子块先无条件放入**，再按距离放兄弟块，避免第一个父块把字数吃满、把后面的命中块挤掉。单角色最多 1,500 字、单父块最多 1,500 字，按 `chunk_id` 去重；这两个上限只约束后续补充的兄弟块，命中块本身先放，所以极端情况下会略超 1,500 字。
8. **取证据**：`assemble_evidence()`（第 518 行）只在选中 root 内按 `content_type` 找“执行计划/统计输出”；先找已选父块，再找同案例其他父块；两种类型轮转取，最多 3 条。证据不占角色名额。
9. **拼输出**：`search()` 返回角色上下文、证据、缺失角色、候选前三、上下文字数、耗时等字段；CLI 和评测都读这一份结果。

补充：没有角色或角色推断为空时，`search()` 退回“子块全局 top 5”，这就是评测里的 `Global Recall@5` 基线。

## 6. 20 题评测集

### 6.1 怎么来的

- 题目按 1A v2 语料里的**实际章节**编写，gold 用 `section_path` 指定到具体父块，不是从检索结果倒推。
- 每题固定记录：`question_id`、`question`、`topic`、`required_roles`、`gold_root_id`、`gold_parents`（按角色分）、`gold_section_paths`、`required_content_types`。
- 文件：`data/eval/questions.jsonl`。

### 6.2 结构

| 项目 | 数值 |
| --- | ---: |
| 题数 | 20 |
| 主题 | 执行计划 5、索引 5、统计信息 5、SQL写法 5 |
| gold root 数 | 17 |
| 多角色题（≥2 个角色） | 12 |
| 三角色及以上 | 3 |
| 带证据类型的题 | 14 |

### 6.3 两个已记录的例外

1. **doc-001 有 4 题**（q11、q12、q13、q15），超过原计划的“每个 root 最多 3 题”。原因是 1A 语料里“统计信息”标签的块高度集中在 doc-001（该 root 有 30 个统计信息块，其他案例最多 5 个）；为了让统计信息主题有 5 题，保留了这个例外。
2. **q05、q09 的 gold 案例本身没有题目要求的证据类型。** 两题都要求“执行计划”，但 gold root `case-001`、`case-005` 的子块内容类型只有 SQL/文字，没有 `执行计划`。这不是检索错，是“资料不足”：题目要求的东西原文没有。评测保留原题和原 gold，不通过改题来抬指标；报告里的 EvidenceCoverage 仍按原口径显示 85.7%，同时在预检里给出提示。

### 6.4 这套题的局限

- **只有 20 题，规模小**，不能当成统计显著的结论；它的用途是给下一轮调参/改规则提供同一把尺子。
- **doc-001 的 4 题共享同一个 root**。`CaseHit@1` 只检查 root，不区分章节，所以统计信息主题的 CaseHit 100% 有一部分是“root 容易选中”，不能说明章节级也对；q13 就是 root 对、步骤节错。
- **题目用词和角色词典高度接近**，所以“角色推断完全一致 100%”只说明这 20 题能被规则覆盖，不代表开放问句也能 100% 推断对。
- **q19 和 case-021 语义接近**，见 §9.1；这是数据歧义，不是单纯调参能完全解决的。

## 7. 指标怎么读

| 指标 | 计算口径 | 回答的问题 | 注意 |
| --- | --- | --- | --- |
| `CaseHit@1` | 最终选中的 `root_id` 是否等于 gold root | 选对案例/手册了吗 | doc-001 的 4 题只看 root，不区分章节 |
| `CaseHit@1（推断角色）` | 不喂 gold 角色，用问句规则推断后再选 | 角色推断错时会不会带偏案例 | 本版和喂 gold 角色同为 95% |
| `RoleRecall@3` | 每个有 gold 的角色，看该角色候选前 3 个父块里有没有 gold 父块 | 检索层有没有把正确段落捞进前 3 | 只看候选，不看最终选块；候选每父块只留一个代表 |
| `RoleRecall@3（macro）` | 先算每题角色命中比例，再对 20 题等权平均 | 题目平均表现 | 80% 不等于 80% 的题全中；全中的是 13/20 = 65% |
| `RoleRecall@3（micro）` | 所有角色实例等权，27/35 | 每个角色平均表现 | 本版主看这个 |
| `RoleMRR@3` | 第一个 gold 父块在 top3 的名次倒数；没命中记 0 | 正确段落排得靠不靠前 | 命中但排第 3 只有 1/3 分 |
| `RoleCoverage` | 必需角色里，最终有选中块的比例（不看是不是 gold） | 有没有内容可填 | 100% 只说明“没缺角色”，不代表选对 |
| `RoleGoldCoverage` | 必需角色里，最终选块拿到 gold 父块的比例 | 最终选块对不对 | 比 RoleRecall 更接近报告实际用料；本版 85% |
| `EvidenceCoverage` | 带证据类型题里，要求的 `content_type` 出现在证据列表的比例 | 执行计划/统计输出有没有拿到 | q05/q09 资料不足也计入 0；可评估的 12 题是 12/12 |
| `MissingRoleCount` | 最终仍缺的角色数，均值/最大 | 报告会不会缺栏 | 本版均值 0、最大 0（靠一次补角色兜住） |
| `ContextChars` | 角色上下文 + 证据按 `chunk_id` 去重后的字符数 | 一次报告草稿要读多少原文 | 单角色上限 1,500，但多角色相加会超过；本版均值 1,620、最大 2,961 |
| `Global Recall@5` | 纯子块全局 top5 里，有没有任意 gold 父块 | 不用角色的基线有多强 | 和 CaseHit 口径不同：一个看子块父块，一个看最终 root |
| 角色推断 exact/coverage/Jaccard | 推断角色集合与 gold 集合的比较 | 规则推断准不准 | 20 题全一致，原因见 §6.4 |
| `latency_ms` | 单题一次角色检索（`search()` 内部计时） | 单次检索要多久 | 本机 CPU、单次运行；均值被首次查询预热拉高 |

| 主题 | 题数 | CaseHit@1 | RoleRecall@3 | RoleMRR@3 | RoleGoldCoverage | EvidenceCoverage | ContextChars 均值 | Global Recall@5 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |

几个读法：

- **执行计划主题的 Global Recall@5 只有 20%，但 CaseHit@1 是 100%。** 两者不矛盾：Global Recall@5 要求“纯子块 top5 里出现任意 gold 父块”，角色方案则是先按角色选子块、再选 root；root 选对不等于子块 top5 里一定出现 gold 父块。这个对比说明“只做全局子块召回”在计划类问题上不够，但不能直接当成角色方案整体优于基线的严格证明。
- **索引主题在本套题上最稳**（RoleRecall 90%、RoleGoldCoverage 100%、Global Recall 100%）。
- **SQL写法最弱**（CaseHit 80%、RoleRecall 70%、RoleMRR 51.7%），主要被 q19 拉低。
- **统计信息 CaseHit 100% 要打折看**：4 道题共享 doc-001 一个 root，root 级命中比章节级命中容易。

## 9. 失败与解释

### 9.1 q19：案例选错（gold case-012，选中 case-021）

- 题目：“标量子查询反向改写案例中，问题 SQL 应该怎么改写？”
- gold：`case-012`《[SQL优化]达梦数据库优化案例之反向改写标量子查询》。
- 系统选中：`case-021`《[SQL优化]达梦数据库的标量子查询改写（案例一）》。
- 两个案例都是“标量子查询改写”，主题非常接近；q19 的 gold 角色候选前 3 里没有 case-012 的任何父块，说明不是最后一步选 root 才错的，而是子块候选阶段就没有把 case-012 排上来。
- 本版**没有为了让 q19 命中而改 gold 或改题**。它同时暴露两件事：数据里存在近义案例；当前检索文本只用了子块正文，没有把 `title`/`section_path` 一起参与 BM25/向量编码，标题里的“反向改写”没有被利用。后者是下一轮可以做的改动，本轮不动。

### 9.2 RoleRecall@3 的 8 个角色实例未命中

### 9.3 q13：root 对，但“手动收集”步骤没进 top3

- 题目：“达梦怎么手动收集某张表的统计信息？”
- gold：`doc-001-p021`，章节 22.5.3.2 手动收集。
- 系统 top3：`doc-001-p016`、`doc-001-p014`、`doc-001-p018`，都是 doc-001 的其他统计信息小节。
- 最终 root 仍是 doc-001，所以 CaseHit 为真；但“步骤”这个角色的 gold 父块没进前 3，RoleRecall 和 RoleGoldCoverage 都记 0。
- 当前 BM25 的 token 只来自子块正文，不含 `title`/`section_path`；“手动收集”这种标题词没有进入稀疏检索。这是下一轮最直接的改进候选，但本轮只记录，不改规则。

### 9.4 q05、q09：证据覆盖 0，是“资料不足”而不是检索错

- q05 要求“执行计划”，gold root case-001 的子块类型只有 SQL/文字，没有执行计划。
- q09 要求“执行计划”，gold root case-005 同样没有执行计划类型。
- 所以证据列表为空，EvidenceCoverage 记 0；这不是检索把执行计划弄丢了，而是 gold 案例里根本没有该内容类型。按项目约定，这种情况应降级为“资料不足/需人工确认”。
- 报告里的 85.7% 是**原口径**（14 题都算）；如果只看“gold 里确实有可能取到证据”的题，是 **12/12 = 100%**。本版没有把这两题删掉或改 gold，避免用改题的方式抬指标。

### 9.5 为什么 RoleCoverage 100%，RoleGoldCoverage 只有 85%？

`RoleCoverage` 只看“这个角色有没有选中块”，不看块对不对；缺角色会在选中 root 内补一次，所以基本都能填上。`RoleGoldCoverage` 要求选中的块是 gold 父块，更严格。**100% 不代表检索全对**，报告用料要看后者。

### 9.6 为什么 Global Recall@5 70%，CaseHit 95%？

两者口径不同：

- `Global Recall@5`：全局子块 top5 里有没有任意 gold 父块；只做一次子块检索，没有角色、没有选 root。
- `CaseHit@1`：角色检索 + 选 root 后，最终 root 是否等于 gold root；root 是案例/手册，比父块粗。

所以 95% > 70% 不能简单说“角色方案比全局基线高 25 个点”，但可以说：在这套题上，角色流程选对案例的能力明显强于“纯子块 top5 是否碰到 gold 父块”。

### 9.7 角色推断 100% 不能外推

20 题的用词和 `config/tags.yaml` 的角色词高度接近，规则推断全部一致。这只证明“这 20 题能被词表覆盖”，不证明开放问句、口语化问句、带错别字的问句也能 100%。下一轮如果要扩题，应专门加“不含角色词”的问句来测推断。

## 11. 怎么复现

**必须在项目根目录执行**（Chroma 相对路径检查的要求）：

```bash
# 1. 建索引；chunks/tags/模型变化后必须加 --force
python scripts/build_index.py --force

# 2. 单条查询：人工看角色、选中块、父块上下文、证据
python scripts/search.py --query "这条 left join 和 inner join 混用的 SQL 慢的原因是什么？优化思路是什么？" --show-context

# 3. 只看全局子块基线
python scripts/search.py --query "这条 SQL 为什么没走索引？" --mode global

# 4. 20 题基线评测；会重写 data/eval/eval_metrics.json 和 eval_report.md
python scripts/eval_retrieval.py

# 5. 全部单元测试
python -m pytest -q
```

建议人工重点看这几条：

1. **q01 对应问句**：应选中 `case-009`，角色是原因/办法，证据里应有执行计划。
2. **q13 对应问句**：“达梦怎么手动收集某张表的统计信息？”：这是已知失败样本，root 对但步骤节不对，适合检查父块展开是否还能补到有用上下文。
3. **q19 对应问句**：“标量子查询反向改写案例中，问题 SQL 应该怎么改写？”：这是已知歧义样本，会选中 case-021；用来判断“近义案例”是否需要在数据层处理。
4. **一条没有角色词的问句**：例如只输入“这条 SQL 很慢”，观察是否退回全局检索，而不是硬套角色。

## 12. 还没做什么 / 下一轮可以讨论什么

这一版**没有**做：

- 没有定质量通过线。`RoleRecall@3` 77.1%、`RoleGoldCoverage` 85% 这些数先作为基线，不和“合格线”比较。
- 没有做参数调优（召回深度、角色候选深度、RRF k、名额都还是第一版工程值）。
- 没有做 query rewriting、领域微调（DM-RAG 论文里的思路），也没有做标题/章节路径入索引（本轮针对 q13/q19 发现的工程改动，尚未实施）。
- 没有做报告正文生成。1B 只到“检索出角色上下文 + 证据”，报告草稿生成还没开始。
- 索引目录按约定不进 Git；代码、20 题评测集、指标和报告已提交；人工验证仍要做。
- 没有把 20 题扩成更大评测集；当前结论只对这 20 题负责。

基于这份基线，下一轮最值得先讨论的三件事（按当前证据排序）：

1. **把 `title`/`section_path` 加进检索文本**：q13 的“手动收集”和 q19 的“反向改写”都指向这个；改动小，能直接检验是否把标题信息利用起来。
2. **处理近义案例**：q19 的 case-012 / case-021 需要在评测集或数据层明确边界，否则调参只是在两个相似案例之间来回。
3. **再谈质量线**：先明确“RoleRecall@3 看候选、RoleGoldCoverage 看最终用料、EvidenceCoverage 只看资料具备的题”，再定目标；否则 85.7% 这种被资料不足拉低的数会误导。
